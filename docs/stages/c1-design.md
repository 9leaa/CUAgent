# C1 技术方案

日期：2026-10-01；分支 `c1-computer-use`。前序 C0-01、C0-02 已独立通过。先写本方案，再实现，不提交/推送；保留用户未提交改动。依据原计划第 5 节，不以 C0 成绩替代六类重复评测。

## 固定目标和验收

固定六类：跨应用传递、弹窗处理、窗口变化、输入纠错、较长流程、失败后的重新观察。每类改进前 3 次、改进后 3 次，共 36 次真实模型/VM 尝试。每次独立 run-id，原始成功与失败均保留。同一官方 Desktop、模型、VM、Driver、任务内容、执行权限、30 次实际请求预算和 verifier 标准；仅被评估的行为增强可变化。六类均至少一次独立成功，逐轮报告成功率、人工介入、请求数、耗时及失败分类；无可重复收益的新增组件不进入默认配置。

## 用例（首次运行前冻结）

| case-id | 任务与独立证明 |
|---|---|
| cross_app | 计算器 GUI 完成 7+8，把新显示传入独立原生接收窗口并提交。核对两进程身份、计算器轨迹/显示、输入实际来自观察、接收字段/提交、result.txt 与独立期望 15；不能自算或共享剪贴板 |
| popup | 原生任务触发确认弹窗，模型观察后确认再读回状态。核对实际打开/确认轨迹、新状态及 fixture 记录；弹窗只授权固定标题、同 PID 与已审查确认操作 |
| window_change | 原生任务从源窗口切到不同 CGWindowID 的目标窗口，模型重新观察并在目标窗口提交标记。旧窗口/快照不能继续派发；核对两个窗口身份及实际目标提交 |
| input_correction | 任务预填错误文本，模型观察后纠正固定字段为 cedar-42 并提交。核对最初错误、新字段、修改轨迹、提交文件与读回，不能忽略错误直接生成文件 |
| long_workflow | 原生三步流程：填写固定文本、进入下一页、完成第二项选择/输入、再确认提交。每步单动作、新观察；核对完整阶段迁移和字段结果，不把一键脚本当长流程 |
| reobserve_failure | 在已授权界面发生一次预定无副作用 stale-target 拒绝后，模型用新观察定位并完成提交。核对真实失败、失败后新 snapshot、实际成功动作和产物；拒绝计预算，不能自动重试旧动作 |

fixture 是真实 UI 与效果记录，不承担模型决策。跨应用必须实际系统 Calculator 与另一个 PID，不用同一窗口两个字段冒充跨应用；弹窗与窗口变化必须真实独立窗口。固定故障只验证重观察，完整超时/退出/权限/接管恢复在 C2，不提前宣布。

## 实施顺序

1. 冻结六例注册表、成功判据、许可应用/窗口/字段/按钮及 run 证据格式；先写边界测试。扩展 guest 执行适配与 AppKit fixture，不改 Harness 主循环。固定应用/窗口选择工具只接受注册表目标，内部真实 Driver 请求全部计数。
2. 基线实现提供完成六例所需的同一工具能力与安全检查，沿用 C0 观察→单动作→新观察。先跑每例三次，冻结全部 baseline 报告。基线失败不得删除或补跑替代原三次。
3. 根据基线失败分类及实际成本确定增强：观察不足、目标定位、决策、动作未生效、验证不足。只改有证据的问题，不预先引入另一规划循环、Agent-S/Jev 或多 Agent。必要组件的接口/mock 可提前准备，行为增强不得混入 baseline。
4. 用同一六例再各三次。独立 verifier 按实施前冻结判据核对 UI、轨迹、文件、独立期望与原预算。报告 baseline/after 配置摘要和每次 run/session/source hash；耗时从 host 启动至终止/验证，不能混用 guest 时区；人工介入逐次记账，不把开发修复宣称为零介入。
5. 只有六类与前后评测、全部失败留存、边界回归齐全后，写 C1 总结、更新 README/PROGRESS，再建 C2 分支和方案。全目标仍为 C0-01→C0-02→C1→C2。

## 不可放松的边界

无宿主桌面操作、目录/剪贴板共享、任意 shell/网络/键盘入口或模型访问 verifier。每任务 30 次观察/失败/拒绝/内部请求；停止之后无新准入，在途单独记录。任何动态目标都重新核对应用可执行路径、PID、窗口清单与新截图/AX；副作用 UNKNOWN 先观察，不盲重放。Driver 返回只算尝试，实际完成需新效果证据。模型不能写审计/截图/报告，独立 verifier 与模型通道分离。证据缺失为非成功。

启动前诊断补记：输入纠错真实通过；第一轮 popup 因 NSPanel 默认失焦隐藏无法绑定，随后 VM 自动锁屏（独立 VNC 新画面确认），已停止保留失败，不计正式 baseline。fixture 设置 hidesOnDeactivate=NO，使测试弹窗在后台输入场景保持真实可见；仍要求唯一同 PID/应用窗口及新 AX。解锁沿用已授权测试账户，临时 caffeinate 限时两小时，不改永久系统设置。baseline 尚未冻结，诊断修复不混入 baseline/after 成绩。

第二轮 popup 已有真实确认效果，但重复 Open 的返回被当成重复完成，轨迹 gate 不通过，失败报告保留。将 C0 Save 的尝试/完成分离推广到 C1 GUI：返回只记 attempted_action；只有新观察证明独立目标窗口、流程下一页或实际提交状态/文件，才关联一次完成事件。完整完成轨迹与 verifier 标准不放松，所有尝试仍保留。不把该诊断报告倒改为成功。

## 基线成本支持的候选增强（实施前）

正式 popup 三轮已独立通过，raw 为 21/18/19；轨迹中 Open Confirmation 尝试分别 4/2/2 次，而真实 popup-opened 效果每轮仅一次。候选为观察提示，不增加规划器或自动输入：仅在 popup 的主窗口、新观察且已有 Open 尝试尚未观察到确认窗口时，额外调用一次同 PID 的窗口清单，确认唯一可见的 reviewed Confirmation 窗口后，返回其完整标题及“选择后重新观察”的提示。该内部请求也计入原 30 次；不把窗口清单当作确认窗口截图，不自动选择、点击或确认。

基线完整 18 次结束前不改运行代码。after 使用显式开发侧开关，默认关闭；任务、模型、fixture、底层权限/预算、成功判据不变。完成全部 after 18 次后，只有 popup 至少 2/3 轮低于基线 raw 中位数 19、平均 raw 下降、各类成功表现不退步且安全回归通过，才允许默认启用候选；否则保留基线默认行为并如实报告无可重复收益。
